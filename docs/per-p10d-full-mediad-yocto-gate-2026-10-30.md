## Test positif, négatif et critères de passage AVANT modification

1. **Positif compilé** : assembler P10A/B/C sur `git archive` OEM, installer uniquement les **en-têtes GStreamer Linux Ubuntu 24.04 dans le runner CI**, `cargo check -p mediad --lib --bins --locked` puis `cargo build -p mediad --bin mediad --locked` **sans stub de `Frames` ni faux GStreamer**, et `cargo test -p mediad --lib --locked` avec la suite constructeur réelle; vérifier `file` sur le binaire, pas son démarrage sur une fausse caméra. Conserver la rétrocompatibilité du détecteur OEM en exécutant ses tests `duck-detect`.
2. **Positif ARM64** : réutiliser le **`scripts/cross-sysroot.sh` officiel épinglé** pour une compilation `cargo check --target aarch64-unknown-linux-gnu -p mediad --lib --bin mediad` avec headers/libs **Debian trixie ARM64**, `rustc` outil 1.89.0, `pkg-config` strictement contre le sysroot. Pas de linkage/runtime/installation Yocto déduits de `cargo check`.
3. **Audit source-only Yocto positif** : cloner en lecture seule `microduck_yocto@1ee58387` dans l'espace éphémère CI, vérifier révision et empreintes Git exactes de `microduck-daemon.bb`, `onnxruntime_1.28.0.bb`, `kas/microduck.yml` ainsi que les invariants : mediad inclus dans build, mêmes dépendances GStreamer, `onnxruntime` en recommandation seulement, version/commit release requis, aucun overlay importé depuis Companion. Le contrôle retourne explicitement `source_contract_ok_deployment_blocked`, **pas `ready`**.
4. **Négatifs et régressions** : tests de revue source refusant `SRCREV`/recette/version non épinglés ou altérés, remplacement d'une dépendance GStreamer, promotion de `RRECOMMENDS` en preuve d'installation, présence d'un poids `.rknn`/`tail.onnx` non autorisé, perte de désactivation par défaut et duplication du thread/caméra. `git diff -- upstream/` reste vide, `robotd`/SQLite/service inchangés. Tous les contrôles PR Python et inventaire requis verts sur **commit final**.
5. **Arrêt** : si environnement GStreamer/ARM64 manquant ou build cassé, diagnostiquer la raison exacte et corriger seulement notre adaptateur ; ne jamais adapter le code OEM épinglé ni inventer une bibliothèque cible. Si construction Yocto complète exigerait un *fork/release* signé ou une licence en attente, **STOP** à ce bord : documenter la demande de décision plutôt qu'ajouter un installateur moteur, un second daemon ou vendre une image Yocto « prête ».

## Matrice et décision

**Réutiliser** : `mediad` entier, ses bibliothèques et `scripts/cross-sysroot.sh`, la recette Yocto du constructeur, P10A/B/C/P7/P9. **Adapter** : uniquement scripts de contrôle/CI et documentation de l'écart de livraison. **Créer** : au plus un préflight read-only des recettes sans exécuter BitBake ni installer de modèle, plus une CI qui compile le **vrai mediad**. **Pas de nouveau pilote, caméra, moteur, SQLite, service, API externe ou sous-module modifié**. Retour arrière : supprimer la branche/PR, aucune installation persistante.

Succès restreint = `mediad_complet_compile_host + check_ARM64_Debian + Yocto_source_contract_verified`. Cela **ne prouve pas** `bitbake`, une image RAUC, le runtime NPU/ORT vrai, la concordance numérique P8, RSS/thermie, ni un robot. **État de déployabilité reste bloqué** tant qu'un release de source Companion, l'intégration vérifiée par BitBake, les droits des poids et les mesures matérielles ne sont pas résolus.
