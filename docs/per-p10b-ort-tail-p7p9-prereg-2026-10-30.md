# PER-P10B — RKNN dix sorties → session ORT OEM → masques P7/P9 (préenregistré, 30/10/2026)

## Porte avant code

**But V1 concret :** un traitement logiciel synchronisé des dix tableaux f32 **déjà produits par l'API P10A**, interprétés par **une session ONNX Runtime** avec la configuration **existante** de `duck-detect::onnx` (`ort=2.0.0-rc.11`, `load-dynamic`, 2 threads max), puis décodés par l'unique noyau Rust P7 et projetés par P9 dans les pixels d'image OEM upright. Une région résultante reste un **candidat visuel incertain**, sans source caméra authentifiée, aucune identité, distance, effet ni autorisation moteur.

**Révision de départ :** `main@6bc4f01c77a300b6ec7eaf1e34668f23fb33f8a5`; sous-modules épinglés `microduck@942e58e3aa6dbb28e7037203fff11866122c7567` et `microduck_rl@b02fdea4902c2b93b7d34a83a6f05da4ececb7d3`, inchangés. Le OEM `duck-detect/src/onnx.rs` ouvre déjà une session `ort` avec `with_intra_threads(2)`, `Tensor::from_array`, `session.run`, `try_extract_tensor::<f32>`. `duck-control/src/policy.rs` vérifie types/noms/dimensions et signale que la bibliothèque dynamique absente ou incompatible peut provoquer un panic `ort` : la vérification/initialisation du runtime reste un point de déploiement à gérer. P10A/#221 fusionnée n'a **pas** relié ses dix sorties au tail. P6/#216 a seulement généré `tail.onnx` en CI PC à partir du poids AGPL, sans livrer de fichier `tail.onnx` déployable ; P7/P9 sont **purs Rust**. P8/#218, échec `InvalidBox`, n'a **pas** établi la parité Rust/RKNN.

## Réutilisation, périmètre, risque

- Réutiliser **sans mise à jour** le code du runtime `ort` et les règles de session `duck-detect/src/onnx.rs`, le contrat P10A de dix sorties, les masques `rust/kwipi-seg-mask-core` P7/P9, le mécanisme d'archive OEM de P10A, et le générateur P6 sans appeler les poids.
- Adapter une seule interface Rust `duck_detect::seg_tail::Tail` : `open(tail.onnx)` et `process([Vec<f32>; 10], UprightFrame) -> Vec<ProjectedRegion2d>`. Dépendance locale vers le crate P7/P9, dans **l'archive temporaire** du code OEM pour tests, jamais dans le gitlink lui-même. Une nouvelle compilation du `Cargo.lock` de cette archive sera nécessaire pour ajouter la dépendance locale ; ne pas modifier le `Cargo.lock` constructeur versionné. `tail.onnx` réel n'est **pas** inclus.
- Ne **pas** ouvrir une caméra, un second `librknnrt`, une seconde SQLite, un thread, socket, service ou passage robotd. Ne pas modifier `mediad`, `robotd`, configuration, poids, modèles, gitlinks ou états mémoire.
- Les 10 entrées f32 P5 représentent **1 793 600 éléments / 7 174 400 octets**, auxquelles s'ajoutent des buffers ORT, les deux sorties f32 et les masques (≤256 000 octets). Ce n'est pas un budget RSS réel. Éviter de copier ces entrées avant `Tensor::from_array` : transférer la propriété des Vec. En cas de forme, nom, type, NaN, limite ou source erronés, ne publier **aucune** région.
- La compilation ARM64 prouve la **compilabilité**, pas l'installation/l'exécution de `libonnxruntime.so` sur une image Yocto. Le décodeur **ne répare pas** la parité P8, aucun nouveau test photographique n'en est déduit. Aucun poids/graphique privé envoyé sur GitHub ; modèle ONNX de tests produit synthétiquement en CI puis détruit.

## Critères gelés avant essais

1. **Porte positive fonctionnelle, sans poids ni photographie :** créer dans `RUNNER_TEMP` un modèle ONNX synthétique de dix entrées aux **noms exacts et aux formes** rapportées par P5/P6, deux sorties `output0[1,300,38]`, `output1[1,32,160,160]`. Exécuter **réellement** ce modèle avec le `ort` Rust **de la version OEM**, en utilisant la bibliothèque binaire Microsoft ONNX Runtime x64 1.28.0, téléchargement vérifié avec SHA-256 officiel `a3e1b79d7bb1bf09696ce675f49e4064e6c81f6202b8225624fff0e93f8d6407` (test PC, pas embarqué). Le modèle fabrique un seul candidat artificiel score 0,9, classe numérique 32, boîte `[240,80,280,120]`, coefficient 1 sur prototype canal 0; la région projetée à la vue `720×1280` `scale=0,5,pad_x=140,pad_y=0` doit contenir **100 cellules** et boîte `[200,160,280,240]`, centroïde `[240,200]`. Deuxième exécution avec score sous seuil ou prototype nul => **aucune** région.
2. **Négatifs exécutés :** absence ou mauvais ordre du nom d'une entrée, rang/forme ou type d'entrée invalides, sorties manquantes ou de mauvaise forme, compte 9 ou 11, tableau brut raccourci, NaN/Inf sur n'importe quelle entrée, `UprightFrame` mal formé et candidat impossible doivent refuser **sans sortie**. Avant une exécution ORT, les buffers doivent être validés (dans le processus appelant). Ne pas cacher les échecs en mode test ignorer/skip.
3. **Intégrité** : `git archive` du SHA OEM précis seulement ; application du patch P10A dans cette archive ; l'extension P10B n'altère pas l'original ou les gitlinks, refuse le blob non conforme et interdit un deuxième patch ; les tests Python de P10A restent verts. Le chemin mono-classe `duck_detect::onnx::Model` et `duck_detect::rknn::Model` historique reste inchangé.
4. **Compilation et régression** : `cargo test -p duck-detect --lib`, `cargo clippy -- -D warnings`, Rustfmt, vérification de compilation `aarch64-unknown-linux-gnu` de `duck-detect` dans la copie OEM. Autres CI habituelles Python + inventaire de paquet **vertes sur le commit final** avant fusion. Ne pas compter un simple checker ONNX Python comme exécution ORT Rust. Si bibliothèque native, test, dépendance ou compilateur indisponible, état `inconnu/en attente` et pas de fusion.
5. **Arrêt** : erreur de forme, de copie/provenance, panic ORT, test réel insuffisant, cache incompatible, performance non mesurée sur cible, violation de sûreté ou licence => arrêter le lot ciblé sans régler a posteriori avec une photographie ni télécharger un autre modèle.
