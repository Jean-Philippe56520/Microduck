## Comparateur, limites et choix technique

**Comparateur OEM actuel :** le détecteur mono-classe existant (une sortie, `Model::open`, `Model::infer`) et ses tests doivent **continuer à fonctionner identiquement**, avec `duck_detector.enabled=false` par défaut. **Choix :** une **extension ciblée** de son seul wrapper `rknn`, pas un second binding RKNN/C ABI. Pour ne pas toucher le sous-module, conserver une petite source Rust additionnelle et un script à ancres exactes qui les assemblent **seulement dans une copie éphémère `git archive` de l'OEM pin** en CI. La source épinglée elle-même et les gitlinks restent inchangés ; aucune installation et aucun chargement de modèle.

**Gains vérifiables :** API explicitement distincte `Model::open_segments` / `infer_segments`, reconnaissant exclusivement la forme P5 des **10** sorties dans leur ordre, et renvoyant les sorties float32 déquantifiées en mémoire transitoire. Conserver la voie mono-sortie inchangée ; interdire un appel `infer` classique sur un modèle à dix sorties. Budget contractuel des buffers de sortie **7 174 400 octets**, hors buffers runtime et anciennes allocations ; **pas** une mesure RSS cible. L'étape future transmettra ces tableaux, dans le même ordre, au `tail.onnx` / ORT puis P7/P9. **Pas de thread lancé et pas de connexion `mediad` dans ce lot**.

## Portes de tests fixées

1. **Positif logiciel** : le script refuse toute source dont le blob Git ne correspond pas à `6260c49f0df9a048d42dca229e53467c77f8139c`, adapte l'archive *temporaire* du pin exactement une fois, conserve `Model::open`/mono. Exécuter vraiment `cargo test -p duck-detect --lib --locked` dans cette archive modifiée ; **tests mono existants** + nouveaux tests pos/neg Rust doivent tous passer.
2. **Positifs Rust préfixés** : dix métadonnées de formes P5 strictement ordonnées et longueur totale 1 793 600 ; dix buffers factices f32 finis de tailles exactes copiés dans le même ordre et sans média, rang/canaux conservés ; entrée originale 640×640×3 attendue en mode seg.
3. **Négatifs Rust préfixés** : 9 ou 11 sorties, formes permutées, longueur fausse, type/pointeur nul, taille non multiple ou incorrecte, NaN/Inf dans la copie, erreur avant publication ; `Model::infer` monoclasse interdit pour un modèle 10 sorties. Les résultats du runtime seront libérés après `outputs_get` même si la validation de données échoue ; un échec `outputs_get` n'autorise jamais un résultat partiel.
4. **Négatifs d'intégrité Python** : la source invalide ou déjà patchée est refusée, les marqueurs absents sont refusés sans adaptation silencieuse, le répertoire de sous-module lui-même n'est jamais modifié. Pas de contournement par un modèle/SDK alternatif.
5. **CI** : Rust 1.89 ou toolchain compatible OEM, `cargo fmt --check`, tests + `cargo clippy -D warnings`, `cargo check --target aarch64-unknown-linux-gnu -p duck-detect --lib` **si l'environnement cible peut le compiler**, et tests du script. Si la compilation croisée réelle exige un sysroot non fourni, consigner le blocage plutôt que le présenter comme réussite. Tests Python généraux et inventaire de paquet restent requis avant fusion. **Arrêt** : divergence forme/ABI, test négatif raté, compilation absente ou CI rouge => pas de fusion.
6. **Après succès seulement** : raccord à la session ONNX Runtime OEM `tail.onnx` et modèle de données P7/P9 dans une autre PR, puis test du chemin `mediad` existant, intégrité de la source et compilation Yocto. **Aucune** revendication NPU exécuté, débit 2 Hz, RAM RK3566, thermie, sécurité moteurs 50 Hz, vision fiable ou observation authentifiée avant robot réel.
