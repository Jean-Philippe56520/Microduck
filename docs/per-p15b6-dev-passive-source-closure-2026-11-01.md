## Porte « objectif → preuve → décision », fixée AVANT le code

**Objectif utile et borné.** Prouver que le processus passif PC de Kwipi P15-B1/B5 peut **être importé et exécuté depuis un ensemble de sources clos, sans dépendre du checkout complet**, afin de préparer son empaquetage séparé en Yocto DEV. Il restera explicitement **mock-only**, non lancé automatiquement, et sans accès aux sockets, moteurs, caméras et modèles OEM. Le paquet de base P14B doit rester **octet pour octet le même contrat de 19 modules** ; seuls les nouveaux modules réellement nécessaires seront fournis par un *add-on séparé*, **non sélectionné dans aucune image**. L'objectif du lot n'est pas de produire une nouvelle WIC, une recette déjà compilée par BitBake ou le runtime OEM authentifié.

Gitlinks `upstream/microduck@942e58e3aa6dbb28e7037203fff11866122c7567` et `upstream/microduck_rl@b02fdea4902c2b93b7d34a83a6f05da4ececb7d3` inchangés. Le témoin à tester est donc un environnement Python n'ayant que les 19 fichiers déjà sélectionnés ; un import de `microduck_companion.passive_fixture_runtime` doit échouer. À l'inverse, **les cinq modules candidats**, déterminés par les imports du lanceur et les dépendances de F2-D, sont `passive_fixture_runtime.py`, `passive_resilience.py`, `offline_resource_budget.py`, `passive_media_fixture_reader.py` et `passive_media_router.py`. Ils ne doivent jamais remplacer l'un des 19 fichiers P14A, créer une deuxième `__init__.py`, charger un modèle ni créer un service.

**Réutiliser / adapter / créer** : **réutiliser** `p14a.current_source` pour les 19 octets audités, `p14b._tar_bytes` pour l'archive déterministe, `ExperienceMemory` et `PassiveCycleSupervisor` sans changement ; **adapter seulement la sélection de sources** via un add-on distinct et opt-in ; **créer un générateur/vérificateur de sources fermé** et ses tests de contenu + exécution isolée. Les recettes OE et les sources externes restent des **données à comparer** ; ne rien copier ni installer depuis une source communautaire, aucun changement OEM/Robotd, P14A/P14B ou système Yocto. Fermeture locale d'import AST : exclure tout import interne manquant sauf les **deux modules historiques Mock** dont les sites optionnels sont déjà vérifiés dans N6. Les dépendances runtime split Python de la distribution ne seront **pas** déclarées validées par des tests hôte.

### Hypothèses, risques, retour arrière

- Hypothèse : les 19 modules déjà approuvés + exactement ces cinq modules suffisent à **importer** le lanceur passif et à faire **un cycle de fixture UNIX** dans un processus Python **isolé de tout checkout**, avec une seule SQLite et un seul statut de détection non fiable. La comparaison à l'ancien paquet ne doit toucher aucun des 19 SHA.
- Risques négatifs : import dynamique non connu ou API mock cachée ; fuite de modules `sim`, `robotd`, modèles ou dépendance tierce ; **confusion des noms de paquet Python** entre socle et complément ; collision de fichiers sur la même directory de site-packages ; tests qui importeraient le checkout au lieu de l'archive ; archivage nondéterministe et symlink ; création d'un `systemd`, d'une `bbappend` prod ou d'une autoactivation. Une version de Python hôte n'établit pas la compatibilité `python3.14` ni les RDEPENDS OE de cible.
- L'échec BitBake initial [#230, run 41144655887](https://github.com/Jean-Philippe56520/Microduck/actions/runs/41144655887) est **un timeout `1200s` (exit 124, à 488/522 tâches, compilation `cmake-native`)**, et **non** un diagnostic d'erreur du code Kwipi. Le `do_package` local WSL2 P14B et la WIC P16 ont déjà été annoncés vérifiés séparément ; **ne pas les relancer à cause de ce timeout CI**. Aucun accès à ces artefacts locaux n'est présumé depuis GitHub.
- Retour arrière : supprimer uniquement le générateur add-on, ses tests, sa doc et sa branche, sans toucher à `upstream/`, P14B, `robotd`, images, mémoire SQLite de l'utilisateur, clés ou modèle.

### Tests NÉGATIFS préenregistrés avant exécution

- Une source manquante, symlink/hors checkout, `__init__.py` dupliqué, module de base dans l'add-on, ajout moteur ou `mock_cycles`, altération des octets, archive avec membre extra, digest/provenance trafiqué, fichier `*.bbappend` ou `systemd`, couche destination déjà présente, staging dans le repo ⇒ STOP sans modifier source.
- Un import relatif non résolu ou une nouvelle dépendance dynamique non revue ⇒ STOP. Le vrai `/run/mediad` ou `/run/robotd` est refusé par la CLI et reste non accessible même si le paquet est installé.
- Aucun accès réseau, aucun nouveau groupe Unix, aucune ACL, aucun service démarré. On ne doit ni remplacer la version P14B, ni modifier l'image DEV construite, ni signer RAUC. Un succès de test host ne déverrouille aucune action OEM.
