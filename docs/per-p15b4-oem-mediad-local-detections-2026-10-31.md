# P15-B4 — Prototype opt-in de détections locales issues de mediad (31 octobre 2026)

## Préenregistrement AVANT tout code/test

**Objectif observable** : un unique processus `mediad` doit pouvoir republier **les détections qu'il calcule déjà** vers un client Unix local, sans accès WebRTC, caméra supplémentaire, modèle, inférence supplémentaire, capture `media.frame`, RPC moteur ou nouvelle base SQLite. Résultat du lot limité à **prototype de source OEM compilé et testé sur PC**, pas à un capteur robot vérifié ni à un Companion installé.

**Base réellement vérifiée** : `main@eab73e9435dbd217c0e50b9e9ecfd59730a6e068`, PR #241 à `f30652b22dcb8d50d1203db43273e5256cfbad98` (4 CI vertes), PR #240/#239/#235/#231/#230 ouvertes; gitlinks `upstream/microduck@942e58e3aa6dbb28e7037203fff11866122c7567` et `upstream/microduck_rl@b02fdea4902c2b93b7d34a83a6f05da4ececb7d3`, inchangés; Qwen #97–99 déjà fusionnées. Yocto OEM épinglé `microduck_yocto@1ee58387810cebb67ae0d634c351d95024483bce`. WIC/ZST P16 et métadonnées RAUC DEV déjà contrôlées WSL2, RAUC non signé, **aucune reconstruction**.

### Manque prouvé — distinct de P15-B2/B3

- `mediad/src/detect.rs` OEM épinglé : `Detector.sightings: broadcast::Sender<Arc<Sighting>>` (buffer 8) envoie chaque résultat de **son seul worker** à la cadence configurée, **détecteur désactivé par défaut**, classe OEM Microduck uniquement. `Sighting` contient `width/height/found/took_ms`, **aucun numéro de séquence ni horodatage de capture**. Le constructeur expose `detect::notification(&Sighting)` en JSON-RPC `media.detections` sans identifiant et avec scores bruts non calibrés.
- `mediad/src/main.rs` : la **seule** souscription est créée par session WebRTC `channel.outbound`. Sans WebRTC, aucune notification de détection locale n'est publiée. `mediad/src/frame.rs` écoute `/run/mediad/media.sock` pour `hello`/`media.frame`, cette dernière demande une trame UYVY brute ; **ne pas réutiliser ce socket pour les détections**, ni ajouter une nouvelle caméra.
- `microduck_companion/passive_media_router.py` : `parse_oem_shape_notification` sait déjà traiter **exactement** la notification OEM et conserve la classe `unknown`, mais seulement sur des fixtures **non authentifiées**, sans souscription réelle; **réutiliser ce décodeur inchangé**.
- `P15-B3` : les droits du groupe Unix `robot` autorisent aussi `robotd` et ses méthodes motrices. Un socket `0660 group robot` serait une régression de sûreté. **Ne pas attribuer le groupe robot à Kwipi** ; ACL du seul socket éventuellement faisable sur Linux mais non persistante après rebind, non intégrée OEM.

### Solution minimale / alternative / limites

**Réutiliser** le `broadcast` constructeur et `detect::notification()`, réutiliser le parseur Python F3-C sans changement. **Adapter temporairement** le code Rust OEM épinglé **dans une archive scratch uniquement** pour proposer une option `--kwipi-local-detections` (booléen, **désactivée par défaut**) lançant, si le détecteur existant a démarré, une tâche Tokio secondaire d'**émission de métadonnées** vers un socket différent : `/run/mediad/kwipi/detections.sock`. Ce n'est ni un daemon ni un nouveau lecteur de trames ; `mediad` demeure l'unique propriétaire du détecteur. Une sous-directory privée `/run/mediad/kwipi/`, appartenant à `mediad` et de mode `0700`, est créée/vérifiée **avant bind** : aucun lecteur tiers ne peut exploiter la fenêtre entre `bind` et `chmod`. Le socket sera owner-only `0600`, **pas `robot`**, et ne traite **aucune requête**, aucun appel moteur ou demande `media.frame`. Quotas préfixés : 2 clients max; au plus 32 boîtes; max 4096 octets par notification; 500 ms pour une écriture; pas de reprise de buffer antérieur lors d'une connexion; retard du `broadcast` => ignorer les événements périmés côté tampon. Aucune permanence, mémoire SQLite, accès WebRTC ou stockage image.

**Ne pas modifier** les gitlinks, binaires, `robotd`, `tofd`, `mediad` du sous-module épinglé, P11/P12, la recette Yocto ou les units systemd : test seulement sur une copie produite par `git archive` dans GitHub Actions. Un socket mode 0600 appartient à `mediad`, donc un service séparé `kwipi` ne peut pas encore le lire ; c'est le **blocage délibéré de production** avant validation du pont P15-B3/OEM. Cette PR ne prétend pas livrer l'accès Kwipi. Aucune licence/dépendance tierce nouvelle : utiliser `tokio`, `anyhow`, `duck-detect`, `tempfile` déjà dans le Cargo.lock constructeur.

**Hypothèse** : un second consommateur du `broadcast` OEM peut transmettre le même `media.detections` sans autre inférence ni effet visible pour `robotd`. **Observation de résultat ≠ preuve de capture récente** : `Sighting` ne transporte pas de `t_ns` de capture ; le client ne pourra certifier que réception locale et cohérence de processus après mise en place d'une authentification Unix/ELF. **La présence d'une boîte/son score ne prouve ni identité réelle, ni catégorie multi-objets, ni sécurité anti-collision.**

### Tests fixés AVANT implémentation

**Clarification de sûreté avant implémentation :** le chemin initial proposé directement sous `/run/mediad/` risquait une fenêtre de connexion avant l'application du mode `0600`, car `RuntimeDirectory=mediad` n'est pas garanti privé. Un sous-répertoire `kwipi/` propriétaire `0700` doit donc exister avant de créer le socket. Le répertoire est créé uniquement par le même processus `mediad` en cas d'opt-in, pas par un second service. La fermeture des permissions est un invariant testé. P10C/P11 peut émettre `media.region_candidates` (propositions SEG), différent du contrat mono-classe : **ce prototype ne transmet que `media.detections`, jamais un autre type**, et ne modifie ni le modèle ni la décision de classe.

**Positifs :**
1. Compilation effective de `mediad` OEM épinglé avec l'adaptation sur archive temporaire Linux/GStreamer ; CLI opt-in vérifiable ; compilation `--lib --bin mediad`, unit tests module + tests OEM `mediad::detect` si possibles. Pas d'exécution caméra ni modèle réel.
2. Faux `broadcast` d'un `Sighting` vers **vrai socket Unix** ; un client reçoit une seule ligne au format exact du sérialiseur constructeur, `method=media.detections`, tailles/boîtes/score brut, aucune image ou commande.
3. Zéro boîte publié en événement (pas d'objet fantôme) ; nouvelle souscription ne rejoue pas la dernière boîte émise ; socket mode `0600` et quotas respectés.
4. La configuration et les sources du détecteur, `robotd`, `mediad/frame.rs`, `Cargo.lock` et gitlinks originaux restent inchangés ; le parseur existant accepte les formes OEM sans promotion de catégories.

**Négatifs :** absence de détecteur/opt-in => aucun serveur démarré; socket déjà présent, fichier normal, symlink ou répertoire parent non sûr => refus de `bind`; `Sighting` invalide (taille, NaN/Inf, boîte inversée, trop de boîtes, message >4096) => aucune émission; second consommateur lent ne ralentit pas le producteur, saturation refuse la connexion supplémentaire; changement d'empreinte OEM/source ou mauvaise archive => script refuse **avant écriture**; duplication de patch => refus. Prover qu'aucune méthode `robot.*`, `media.frame`, requête RPC ni protocole réseau ne peut transiter par le nouveau socket.

**Seuil PASS préfixé :** tests Python de l'overlay, Rust sur **vrai code OEM épinglé** en archive + compilation `mediad` et suite générale Python, P15A/N1/B3 **verts sur dernier SHA** ; aucune régression des protections P14A, aucune dépendance ou nouvel appareil. **STOP** si compilation échoue, si un événement devient une classe reconnue, si permissions élargies à `robot`, si modèle/firmware/moteur/SQLite/GStreamer OEM réinventé ou si un accès réseau est nécessaire. Repli = supprimer un module Rust candidat, script d'injection, tests et CI ; copies scratch éphémères supprimées. **Décision matérielle et P15 déployable reste en attente :** ACL pour UID Kwipi après bind/rebind + identité `DUCK_REVISION` du binaire + livraison dans P11/P12 sous accord + CPU/RSS/température/cadence 50 Hz sur robot. Aucune automatisation d'ACL, systemd ou boot dans ce lot.
